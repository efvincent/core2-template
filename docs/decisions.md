# Decisions

Made by the author unless noted. Carried over from the handoff brief written at the end of the core2 session that planned this repo (`core2/proposals/core2-template-brief.md`).

1. **A separate repo**, not part of core2 (2026-10-30). Each generated client gets core2 as a **git submodule from GitHub, pinned to a release tag**. No local-override mechanism: a core2 change needed while working on a client is made in core2 through core2's own gate (branch, tests, review, release, tag), and then that client's pin is bumped. Other clients stay on their pins.
2. **Claude writes the template**, all of it: `cargo-generate.toml`, the hook, `setup.sh`, the Makefile, the `main.cpp` variants, `check.sh`, the READMEs and docs (2026-10-30). In core2, by contrast, the author types `src/`, `examples/` and the `Makefile`. In a generated client the author owns `src/` and the `Makefile` again (the CMake build since decision 12).
3. **UI choice:** `plain`, `ncurses`, `sdl3`, `imgui`. For `imgui` a second question asks for the backend, offering all four: SDL3 + SDL_Renderer, SDL3 + SDL_GPU, GLFW + OpenGL3, GLFW + Vulkan (2026-10-30).
4. **No tests in generated clients for now.** A more robust test harness is planned in core2 later; nothing here designs for it yet (2026-10-30).
5. **The comment-only hook is referenced from the submodule**, not copied: `python3 "$CLAUDE_PROJECT_DIR"/third-party/core2/.claude/hooks/comment_only_guard.py`. If the submodule is not checked out, every `Edit`/`Write` is blocked (fail closed); the client's README and `CLAUDE.md` say to run `git submodule update --init` (2026-10-31).
6. **The style is imported from the submodule:** the client's `CLAUDE.md` has `@third-party/core2/docs/style.md` (2026-10-31). `style.md` says a client's modules use `<project>::<name>` namespaces with helpers in `detail`. That rule began as Claude's extrapolation from core2's `base::<name>`; the author confirmed it on 2026-10-31.
7. **Generator: cargo-generate** (0.23.13 installed; `copier` was considered and not chosen) (2026-10-31).
8. *(Superseded by decision 14 on 2026-11-17.)* **Submodules come from a one-time `setup.sh`, not the post hook** (2026-10-31). The brief had the hook run `git submodule add`; cargo-generate runs hooks in a temp dir and drops every `.git` directory when it moves the result, so that cannot work (details in [design.md](design.md), "Why setup.sh, not the hook"). The hook renders `setup.sh` with the URL and tag; the author runs it once after generating, and it deletes itself. Chosen over a wrapper script and a Makefile bootstrap.
9. **The client protects core2's sensitive parts the way core2 does** (2026-10-31). The client's `.claude/settings.json` blocks core2's directories as core2's own settings do (`denyWrite` on `third-party/core2/src`, `tests`, `Makefile`, and `deny` rules for the edit tools; core2's CMake build in place of its `Makefile` and `core.mk` since decision 12), and its `CLAUDE.md` protects them as core2's `CLAUDE.md` does. Both keep the broader rule that nothing under `third-party/` is edited (decision 1).
10. **`glfw_vulkan` uses the system Vulkan headers** (Arch: `vulkan-headers`), not a pinned `Vulkan-Headers` submodule (2026-10-31). The build stops with an install hint when `vulkan/vulkan.h` is missing (the Makefile then, `CMakeLists.txt` since decision 12).
11. **core2 is fixed from the client's submodule, in a core2 session** (2026-11-01, from core2 `v0.14.0`). Still through core2's gate and a pin bump (decision 1), but without a separate core2 clone: Claude Code is started in `third-party/core2`, so core2's `CLAUDE.md`, settings and hook apply. The client's `CLAUDE.md` scopes its `third-party/` rules to sessions started at the client's root, and `setup.sh` writes core2's git-ignored `.claude/settings.local.json` so Claude can commit there (the submodule's git directory writable, its `hooks/` and `config` not). The default `core2_version` becomes `v0.14.0`, whose `workflow.md` describes the flow.
12. **The generated project builds with CMake only, on core2 `v2.0.0`** (2026-11-15). core2 `v2.0.0` removed `Makefile` and `core.mk` (core2's D45), so a generated make project no longer builds on a current core2. The plan was Claude's; the author approved it, the two choices below included.
    - `template/Makefile` is replaced by `CMakeLists.txt` (`add_subdirectory(third-party/core2)`, `core2::core2`, a `FATAL_ERROR` when the submodule is missing) and `CMakePresets.json` (`debug`, `release`, `lto`, `instrument`; `-DNDEBUG` only in `CMAKE_CXX_FLAGS_<CONFIG>`, as core2's D44 requires). The default `core2_version` becomes `v2.0.0`, also the oldest the template fits.
    - **The variant choice stays in the hook and Liquid**, not a CMake option: `post.rhai` still moves the chosen `ui/<variant>/` to `src/`, and Liquid renders `CMakeLists.txt` with only that UI's block, as it did the Makefile. A `UI` option would ship every variant's sources and build logic to every client, in a file the client's author owns. CMake's `${}` and `$<>` do not collide with Liquid.
    - **UI libraries** through `pkg_check_modules(... IMPORTED_TARGET)`: their flags reach only the targets that link `PkgConfig::ui`, never core2 (the Makefile kept them out of `CXXFLAGS` for the same reason). **ImGui** is a static `imgui` target that does not link `core2::core2` (no `-nostdinc++`, no warnings, `-fno-threadsafe-statics`), with its headers as `SYSTEM PUBLIC` includes.
    - **`gnu++26`, CMake's default**, for the client's files (core2's D43, as in core2's `examples/hello`), at the cost of 24 extra BMI compiles per build directory; `docs/core2.md` names `set(CMAKE_CXX_EXTENSIONS OFF)` to skip them. **`-DBUILD_DEBUG` is dropped**: nothing in core2 or `ui/` used it.
    - `check.sh` configures and builds every preset (CMake warnings fail it too), checks the debug preset's `compile_commands.json` (no `make bear`), that configuring without the submodule stops with the message, and that the submodule stays clean after the builds.
    - The client's settings drop the make allows and core2's `Makefile`/`core.mk`, deny writes to its own `CMakeLists.txt` and `CMakePresets.json`, and name core2's CMake build, `tools/` and `bench/support/` (core2 `v2.0.0`'s own `denyWrite` and hook). `setup.sh`'s core2 `settings.local.json` step is unchanged: core2 `v2.0.0` still git-ignores that file and its `workflow.md` still describes it.

13. **Editor, docs and README additions** (2026-11-16, the author's picks):
    - clangd runs with `--header-insertion=never` (completion would add standard-library `#include`s), `--background-index` and `--completion-style=detailed`.
    - `core2_version`'s regex accepts only major version 2 or later, so a tag without the CMake build is rejected at generate time; `CMakeLists.txt`'s missing-submodule message also names a pin older than core2's CMake build (`v1.1.0`).
    - The client's README notes clang 23's missing debug info for core2 templates instantiated across modules, with the workaround; how to pass arguments under F5 (`args`, `promptString` inputs) is in the README, not in `launch.json`.
    - The client ships `docs/Doxyfile` and a `docs` target (fails on any Doxygen warning, as core2's); `/docs/html` and `/docs/latex` are git-ignored, and so is `.idea`. Each variant's `main` is documented so the target passes in a new client.
    - Small text: "Claude does not push: the sandbox blocks `github.com:22`"; the `CMakeLists.txt` header says an edit in `third-party/core2` is picked up by the next build; `-g` in `release` and `lto` is for profiling.

14. **Copier, not cargo-generate; one command does everything** (2026-11-17). The author's requirement: generating a project leaves nothing to run by hand, `setup.sh` included, with core2's HTML reference built and linked. cargo-generate cannot (its hooks run before the move, which drops every `.git`, and nothing runs after; design.md, "Why Copier"); the author rejected a wrapper script and a folder-open task, and chose Copier over Cookiecutter (Claude's recommendation: tasks run in the destination, only `*.jinja` is rendered, `copier update`). The plan was Claude's; the author approved the move.
    - `copier.yml` holds the questions (`project_name`, from the destination's name, replaces cargo-generate's `project-name`) and the task: `sh setup.sh` in the new project, on `copy` only. `--trust` is required for it.
    - The submodules stay (decisions 1 and 11 unchanged). `setup.sh` stays in the client (as `./dev setup` since decision 15) and becomes rerunnable: tools first, `git init` if needed, a new submodule at its tag, an existing one only at its recorded pin, core2's `settings.local.json` every run, then the debug build and `core2_docs`. It replaces the manual `ln -sf`, the `settings.local.json` command in the client's `docs/core2.md`, and the self-deleting script.
    - core2's reference: a `core2_docs` target runs the submodule's own Doxyfile with the output in the client's `docs/core2/` (git-ignored), and a tag file through which the client's `docs` links core2's names. The client's README links it at the top. Doxygen becomes a prerequisite.
    - VSCodium: `.vscode/extensions.json` (clangd, CMake Tools, CodeLLDB), CMake Tools on the presets. CMake Tools cannot be given a default preset from a project file, so the first open asks once.

15. **`./dev`, and the controls protected** (2026-11-17, the author's requirements; the design is Claude's).
    - The client gets one short command, `./dev` (POSIX `sh`, executable as generated), over the presets: `build`, `run`, `docs`, `clean`, `setup`, `help`; it asks for a missing command or preset at a terminal and never elsewhere. `setup.sh` becomes `./dev setup`, which Copier's task runs; `build`, `run` and `docs` check that the setup is done and offer it. Chosen over `just` (another prerequisite) and a Makefile front end.
    - `./dev` is the author's, like the build: `Edit(/dev)` denied and `./dev` in `denyWrite`. core2's hook cannot check a shell script, so not even comments.
    - In the client, files that are the author's get patches, never edits: C++ in chat for the author to type, or files in `proposals/`; the code without line numbers, each patch naming the file, the lines and a couple of unchanged lines of context.
    - `CLAUDE.md` and `.claude/` are the author's controls, in the client and in this repo, as in core2: denied to the edit tools and to Bash (`denyWrite`), and changed only through a patch file in `proposals/` (a unified diff, checked with `git apply --check`) with the command to apply it. Controls that Claude could change would not control anything.
    - This repo's `.claude/settings.json` runs Claude Code's Bash in the sandbox: writes only inside the repo (not `CLAUDE.md` or `.claude/`) and `$TMPDIR`, network only to `github.com`.

16. **Releases are tags, with a changelog** (2026-11-17; the convention is Claude's proposal, the author asked for it). `v1.0.0` is the first, the Copier template as merged.
    - A merge to `main` that changes what a generated project gets (`template/`, `copier.yml`) is released: a `CHANGELOG.md` entry on the branch, under `[Unreleased]` until the release commit names the version and date, then the author tags the merge `vX.Y.Z` and creates the GitHub release with that entry as its notes. A merge that changes only this repo (its docs, `check.sh`, its settings) is not released.
    - Semantic Versioning from the project's side: patch for fixes, minor for additions, major when `copier update` would leave hand work (a renamed or removed question, a moved file the author owns, a build change the author must follow).
    - `copier copy gh:...` takes the latest tag; `copier update` moves a project between tags. A default `core2_version` bump is a minor release (new projects get the newer core2; existing ones keep their pin).

## Claude's choices (2026-10-31; the author may overrule)
- The client's `CLAUDE.md` is stored as `template/CLAUDE.client.md` so it is not loaded as a nested `CLAUDE.md` while working on this repo; the hook renames it.
- The hook moves the whole `ui/<variant>/` directory to `src/` (cargo-generate's `file::rename` needs the target's parent to exist, and the template has no `src/` of its own).
- The client's `.claude/settings.json` adds `deny` rules for the edit tools on `third-party/` (and, per decision 9, on core2's protected paths by name) next to the sandbox's `denyWrite`: `denyWrite` covers Bash only, and the comment-only hook guards only `src/` and the build files.
- The build compiles every `src/**/*.cpp`, not only `main.cpp`, and ships no starter module (the Makefile guarded `core_modules`; `CMakeLists.txt` globs, and an empty module set is fine).
- `check.sh` checks the `core2_version` default from `cargo-generate.toml` (one source of truth); `CORE2_VERSION=...` overrides it to try a new tag.
- The ImGui backend defaults to `sdl3_renderer`.
- The `ncurses` variant prints through core2 when stdin or stdout is not a terminal, instead of failing in `initscr`; `check.sh` relies on it.
- UI libraries' `pkg-config --cflags` stay off core2's compile lines (`CXXFLAGS` under make; `PkgConfig::ui` linked by the project's targets only, since decision 12).
- `check.sh` runs the windowed variants on SDL's offscreen driver where that works, and only builds the others unless `WINDOWED=1`, so it never opens windows on the desktop by default.
- `.vscode/settings.json` points clangd at `build/cmake/debug`, and `setup.sh` builds the debug preset (2026-11-17). Before, clangd looked for `compile_commands.json` at the root, which only a manual `ln -sf` from the client's README put there, and nothing had configured the project yet, so VSCodium opened a new project with no compilation database. The build in `setup.sh` also writes the module files that clangd's flags name.
- The UI variants are directories named `{% if variant == '<variant>' %}src{% endif %}` (2026-11-17), so Copier copies only the chosen one, as `src/`, with no task to move files, and `copier update` sees `src/main.cpp` as a template file like any other.
- The README links core2's reference with an HTML `<a href>`, and the `docs` target links `docs/html/docs` to `..`, so one link works from the README and from the generated main page (design.md, "The client's CMake build").
