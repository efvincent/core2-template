# Design

How core2-template is put together and why. The decisions behind it, with dates, are in [decisions.md](decisions.md).

## Layout
```
core2-template/
  CLAUDE.md, README.md, docs/   this repo
  copier.yml                    the questions, the template's settings, the setup task
  check.sh                      generates the variants, builds every preset, runs the binaries
  template/                     the payload (Copier's _subdirectory); only *.jinja files are rendered
    {{_copier_conf.answers_file}}.jinja   the client's .copier-answers.yml, for `copier update`
    dev.jinja                   the client's one command (executable): build, run, docs, clean, setup
    CLAUDE.md.jinja             the client's CLAUDE.md
    .claude/settings.json       the client's sandbox, permissions, comment-only hook
    .vscode/                    settings.json, extensions.json, launch.json.jinja, tasks.json
    .clang-tidy                 the client's clang-tidy, in core2's style
    third-party/.clang-tidy     no checks in the submodules
    .gitignore.jinja
    CMakeLists.txt.jinja        on core2's core2::core2 target (only the chosen UI's block), docs and core2_docs
    CMakePresets.json           debug, release, lto, instrument
    README.md.jinja             the client's README
    docs/                       the client's docs: core2.md.jinja, and Doxyfile.jinja for the `docs` target
    {% if variant == '<variant>' %}src{% endif %}/main.cpp
                                one per variant: plain, ncurses, sdl3, imgui-sdl3_renderer,
                                imgui-sdl3_gpu, imgui-glfw_opengl3, imgui-glfw_vulkan
```

## Questions
In `copier.yml`.

| Name | Values | Default | Notes |
|---|---|---|---|
| `project_name` | `^[a-z][a-z0-9-]*$` (the validator) | the destination folder's name | Names the CMake project, the target and the binary `build/cmake/<preset>/<project_name>`; with `-` as `_`, the client's module namespace. |
| `core2_version` | `vX.Y.Z`, major 2 or later (the validator) | `v2.1.8` | The core2 tag to pin; an older tag is rejected at generate time, `--data` included. The default is the tag `check.sh` last passed with. `v2.0.0` is the oldest the generated project fits: its build is CMake only, as core2's is since `v2.0.0` (`v1.1.0` has the CMake target, `v1.2.0` the link-time `NDEBUG` check the docs describe, and both still ship make); its settings name core2's CMake build, and the hook that guards the client's `CMakeLists.txt` is `v2.0.0`'s. |
| `core2_url` | git URL or path | `git@github.com:efvincent/core2.git` | Private repo, so SSH. `check.sh` uses it too, unless `CORE2_DIR` names a local clone. |
| `ui` | `plain`, `ncurses`, `sdl3`, `imgui` | `plain` | |
| `imgui_backend` | `sdl3_renderer`, `sdl3_gpu`, `glfw_opengl3`, `glfw_vulkan` | `sdl3_renderer` | Asked only when `ui == 'imgui'` (`when`). |
| `variant` | | computed | Never asked or recorded (`when: false`): `ui`, or `imgui-<backend>`. Picks the `src` directory. |

## Generating
`copier copy --trust gh:efvincent/core2-template <dir>`, since 2026-11-17 (decision 14; before, cargo-generate and a manual `setup.sh`, decision 8).
1. Copier clones this repo (its latest tag, or the default branch's `HEAD` while there are no tags; a local path includes the working tree's uncommitted changes), asks the questions, and renders `template/` straight into `<dir>`. Only `*.jinja` files go through Jinja (`_templates_suffix`), and lose the suffix: the C++ sources are copied as is, since `{{` is valid C++. Path names are always rendered: each variant's directory is `{% if variant == '<variant>' %}src{% endif %}`, so the chosen one becomes `src/` and the others render to an empty name, which Copier skips. `CLAUDE.md.jinja` is not a `CLAUDE.md`, so Claude Code does not load it while working on this repo. At the switch, before `setup.sh` and the docs changed, the output was the same, byte for byte, as the cargo-generate template's for all seven variants, plus `.copier-answers.yml` (checked 2026-11-17).
2. Copier's task (`_tasks`, on `copy` only, which is why `--trust` is needed) runs `sh dev setup` in `<dir>`. `./dev setup`:
   - checks for its tools (git, python3, cmake, ninja, clang++, clang-scan-deps, doxygen, and pkg-config for a UI) and names the missing ones before changing anything;
   - runs `git init` when there is no `.git`;
   - adds `third-party/core2` as a submodule from `core2_url`, checks out `core2_version` and stages it (the gitlink is the pin), and the same for ImGui at `v1.92.8` when `ui == 'imgui'`. A submodule already in the index is only initialized at its recorded commit (`git submodule update --init`), so a rerun never moves a pin, a bumped one included;
   - writes core2's `.claude/settings.local.json` (below), every run, since its path is absolute;
   - runs `cmake --preset debug`, `cmake --build --preset debug` (the `compile_commands.json` and module files clangd needs) and `cmake --build --preset debug --target core2_docs`.
   It stays in the client as part of `./dev` (below): after a fresh clone (`git clone --recurse-submodules`, or without, since it initializes them) it is the one step, and it is safe to rerun. A failure exits non-zero; Copier then reports the task's failure and keeps `<dir>`.

Nothing is committed: the author makes the first commit, `.copier-answers.yml` included. `copier update` (clean, committed tree) merges later template changes; its task does not run on `update`, so it never moves a pin or rebuilds.

### Why Copier, and the setup inside it
cargo-generate (checked with 0.23.13 on 2026-10-31, and its changelog up to 0.26.0 on 2026-11-17) runs its hooks in a temp dir before the move to the destination, skips every directory named `.git` at any depth in the move (a `.git` *file* survives but points at nothing), runs its own `git init` afterwards, and has nothing that runs after that. So no hook could leave submodules, and a CMake build tree, which records absolute paths, cannot be made before the move either. That is why the cargo-generate template needed a manual `sh setup.sh` (decision 8).

Copier renders into the destination and runs its tasks there, after the copy, so `./dev setup` can do the git work and the builds in place. Cookiecutter's post hook would also work, but it renders every file unless told otherwise and has no update. A wrapper script, or a folder-open task in the editor, were the other ways out of cargo-generate; the author rejected both.

If the submodule is missing (a fresh clone without `--recurse-submodules`), `CMakeLists.txt` stops the configure with a message naming `sh setup.sh` and `git submodule update --init`, and the comment-only hook, which lives in the submodule, blocks every `Edit`/`Write` (fail closed).

## The client's CMake build
Since 2026-11-15 (decision 12; core2 `v2.0.0` removed `core.mk`, its D45). Jinja renders `CMakeLists.txt` with only the chosen UI's block; `CMakePresets.json` is the same for every variant.
- `CMakeLists.txt`: `cmake_minimum_required(VERSION 3.30...4.4)`, `project(<project-name> LANGUAGES CXX)`; a `FATAL_ERROR` when `third-party/core2/CMakeLists.txt` is missing, before `add_subdirectory(third-party/core2)`; `file(GLOB_RECURSE ... CONFIGURE_DEPENDS)` over `src/*.cppm` (a `CXX_MODULES` file set, `BASE_DIRS src`) and `src/*.cpp`, so every `.cpp` can `import core;`; `target_include_directories(PRIVATE src)`; the warnings `-Wall -Wextra -Wpedantic -Wglobal-constructors -Wexit-time-destructors` on the app target only; `target_link_libraries(PRIVATE core2::core2 ...)`.
- No required flags are repeated: `core2::core2` carries `cxx_std_26`, `-fno-exceptions -fno-rtti -nostdinc++` and `-nostdlib++` at link time. The app compiles as `gnu++26`, CMake's default (core2's D43, as in core2's `examples/hello`); CMake then compiles core2's interfaces a second time with the app's flags. The client's `docs/core2.md` says that `set(CMAKE_CXX_EXTENSIONS OFF)` skips that.
- `CMakePresets.json`: a hidden `base` (Ninja, `clang++`, `binaryDir` `build/cmake/${presetName}`, `CMAKE_EXPORT_COMPILE_COMMANDS`), then configure and build presets `debug` (`-O0 -g`), `release` (`-O3 -march=native -DNDEBUG -g`), `lto` (release plus `-flto=full`, with `CMAKE_AR`/`CMAKE_RANLIB` set to `llvm-ar`/`llvm-ranlib`) and `instrument` (`-O1 -g -fno-omit-frame-pointer -fsanitize=address,undefined -fno-sanitize-recover=all -fno-sanitize-link-c++-runtime`; the last flag is needed with `-nostdlib++`). The flags sit in `CMAKE_CXX_FLAGS_<CONFIG>`, which core2 shares in the same build, so `-DNDEBUG` agrees; a target-only `-DNDEBUG` fails to link on core2's mode check (D44). `-DBUILD_DEBUG`, which the Makefile set and nothing used, is gone.
- `release` and `lto` keep `-g` so profiles have symbols (the author's choice).
- The `docs` and `core2_docs` targets are defined when `find_program` finds `doxygen` (`./dev setup` requires it).
- `core2_docs` builds core2's reference and user guide from the pinned submodule into `docs/core2/html/` (git-ignored). At configure time CMake writes `build/cmake/<preset>/core2.Doxyfile`: `@INCLUDE` of the submodule's `docs/Doxyfile`, then `OUTPUT_DIRECTORY` and `GENERATE_TAGFILE` (`docs/core2/core2.tag`) under the client, no LaTeX, no warnings (core2's gate checks them). Doxygen runs in `third-party/core2`, where that Doxyfile's relative paths (the doxygen-awesome theme, `INPUT`) point, with `CORE2_VERSION` from the submodule's `VERSION` (its `PROJECT_NUMBER`). Nothing is written in the submodule (`check.sh` checks it stays clean). About 12 MB for `v2.1.8`.
- `docs` runs `doxygen docs/Doxyfile` from the root, after `core2_docs`. The Doxyfile lists only non-default settings: `INPUT` README, `docs/` and `src/` (`*.cppm *.cpp *.h *.md`, `cppm=C++`), `EXCLUDE` the generated `docs/html`, `docs/latex` and `docs/core2`, README as the main page, `detail` namespaces excluded, HTML only, `WARN_AS_ERROR = FAIL_ON_WARNINGS` (as core2), and `TAGFILES = docs/core2/core2.tag=../core2/html`, so core2's names in the client's pages and sources link into core2's reference. Output `docs/html/`, git-ignored with `docs/latex/`. It lives in `docs/`, which Claude writes in a client.
- The README's link to core2's reference is an HTML `<a href="docs/core2/html/index.html">`, not a Markdown link: Doxygen tries to resolve a Markdown link to a file under an `INPUT` directory and fails (`unable to resolve reference ... for \ref command`), but copies an `<a href>` as written. Written relative to the root, it would point nowhere from `docs/html/index.html`, so `docs` ends by linking `docs/html/docs` to `..`; the same `href` then works from the README in an editor or on GitHub (once built) and from the generated main page. `EXCLUDE` keeps Doxygen from following that link back into `docs/`.
- Every configure writes `build/cmake/<preset>/compile_commands.json`; clangd reads the debug one in place (`--compile-commands-dir=${workspaceFolder}/build/cmake/debug`), and `./dev setup` builds the debug preset so it exists when the editor first opens (before 2026-11-17, clangd looked at the root, where only a manual `ln -sf` put it, and VSCodium opened a new project with no database). The client's README gives the `ln -sf` to the root for other editors. There is no `make bear`.
- Binary: `build/cmake/<preset>/<project-name>`.

## UI variants
Each variant's `main.cpp` uses core2 (`import core;`, `console::println`, `os::args` from `main`'s `argc`/`argv`) in the style of core2's `docs/style.md`. C headers for ncurses, SDL3 and GLFW are fine. While curses owns the screen, nothing goes through `console::print`.

| Variant | What `main.cpp` does | pkg-config packages | Installed here (2026-10-31) |
|---|---|---|---|
| `plain` | prints the arguments | none | |
| `ncurses` | shows the arguments on a curses screen until a key; without a terminal on stdin and stdout, prints them through core2 instead | `ncursesw` | 6.6 |
| `sdl3` | a window drawn with SDL_Renderer (a square moving back and forth) until Esc or close | `sdl3` | 3.4.18 |
| `imgui` + `sdl3_renderer` | ImGui window listing the arguments, a demo-window toggle, a background color, the frame rate | `sdl3` | |
| `imgui` + `sdl3_gpu` | the same, drawn with SDL_GPU | `sdl3` | |
| `imgui` + `glfw_opengl3` | the same, GLFW and OpenGL 3 (`main.cpp` calls `glClear` and friends, hence `gl`) | `glfw3 gl` | glfw3 3.5.1, gl 1.2 |
| `imgui` + `glfw_vulkan` | the same, GLFW and Vulkan, swapchain through ImGui's `ImGui_ImplVulkanH_*` helpers | `glfw3 vulkan`, plus the Vulkan headers | loader and headers 1.4.363 |

Each `main` has a Doxygen comment (`@brief`, `@param`, `@return`), so a new client's `docs` target is warning-free.

The ImGui variants follow Dear ImGui's own `examples/example_<backend>/main.cpp` (v1.92.8, MIT), rewritten in core2's style: errors go to `console::eprintln`, Vulkan errors stop through `trap::panic`, and the state the example keeps in globals is a struct on `main`'s stack (globals with constructors would trip `-Wglobal-constructors`).

The UI libraries come through `pkg_check_modules(ui QUIET IMPORTED_TARGET <packages>)`, and the app links `PkgConfig::ui`. Their compile flags then reach only targets that link it, never core2 (`ncursesw` alone adds `-D_DEFAULT_SOURCE -D_XOPEN_SOURCE=600`), and their include directories are system includes. One exception: CMake's second copy of core2's interfaces (D43's synthesized BMIs) is compiled with the importer's flags, so in `ncurses` it gets ncursesw's defines. Harmless here: with clang++'s `_GNU_SOURCE`, the C headers core2 includes preprocess to the same text and the same macros with and without them (checked 2026-11-15); `CMAKE_CXX_EXTENSIONS OFF` removes those BMIs altogether. `CMakeLists.txt` stops with a message naming the packages when `pkg-config` or the packages are missing.

ImGui and its backends are C++ that does not import core2. `CMakeLists.txt` builds them as a static `imgui` target (the five core files and the chosen backend's two) that does not link `core2::core2`, so it gets none of core2's flags (no `-nostdinc++`) and none of the app's warnings, plus `-fno-exceptions -fno-rtti -fno-threadsafe-statics` (no `__cxa_guard_*`) and `CXX_SCAN_FOR_MODULES OFF`. The build type's flags (optimization, LTO, sanitizers) reach it as they reach everything. `target_include_directories(imgui SYSTEM PUBLIC third-party/imgui)` gives the app ImGui's headers as system headers; `imgui` links `PkgConfig::ui` PUBLIC, and the app links `imgui`. `-nostdlib++` comes from `core2::core2` on the app's link line, as before: all four backends link without the C++ runtime (checked 2026-10-31 under make, 2026-11-15 under CMake).

### Vulkan headers
The Vulkan loader's `vulkan.pc` (Arch: `vulkan-icd-loader`) brings no headers; they are a separate package (`vulkan-headers`). `glfw_vulkan` builds warning-free in all four modes with Vulkan-Headers 1.4.350 (first, through `CPATH`) and with the system's 1.4.363. The project uses the system package (decision 10), not a pinned `Vulkan-Headers` submodule as the old template did: the headers then match the loader `pkg-config` finds, and there is no third pin. `CMakeLists.txt` looks for `vulkan/vulkan.h` (`find_path`, with the `vulkan` package's include directories as hints) and stops with the package names when it is missing.

The old template (`~/code/cpp/project-template`, for the earlier `cpp-core` library) had one Liquid `if/elsif` `main.cpp`; one file per variant lets clangd parse each one, and keeps the template engine away from C++ braces.

## ./dev
Since 2026-11-17 (decision 15). One POSIX `sh` script at the client's root, rendered from `dev.jinja` (the project name, the core2 URL and tag, the UI's tool and ImGui lines). Copier keeps the template file's mode, so the client's `dev` is executable (checked by `check.sh`), and git records it as `100755` in the first commit.
- `build [preset]` runs `cmake --preset <p>` when `build/cmake/<p>/CMakeCache.txt` is missing, then `cmake --build --preset <p>`. `run [preset] [-- args]` builds, then `exec`s the binary from the root; a first argument that names a preset is the preset, and `--` ends `./dev`'s own arguments. `docs` builds the `docs` target (which builds `core2_docs`). `clean <preset>` is that preset's `clean` target, `clean all` removes `build/`. `setup` is the setup above. `help` prints the list.
- At a terminal (stdin and stdout both), a missing command or preset is asked for as a numbered list, Enter picking the first. Elsewhere it never asks: no command prints the help, no preset means `debug`. So the editor's tasks, scripts and Claude Code can call it.
- `build`, `run` and `docs` first check that the setup is done: a git repository, the submodules checked out, and core2's `settings.local.json` naming the submodule's current git directory. At a terminal they list what is missing and offer `./dev setup` (Enter: yes); elsewhere they stop, naming it.
- It only runs CMake, so the CMake commands still work directly, and the client's `CLAUDE.md` allows both.
- `.vscode/tasks.json` has `build-debug` (default), `build-release` and `docs`, each a `./dev` command.

## The client's Claude Code setup
Mirrors core2's (core2's `docs/claude.md`, "In client projects"):
- `CLAUDE.md`: the author writes `src/`, the CMake build (`CMakeLists.txt`, `CMakePresets.json`), `./dev` and `.clang-tidy`; Claude writes `docs/` and offers changes to the author's files as patches: C++ in chat for the author to type, or files in `proposals/`; the code has no line numbers, and each patch names the file, the lines and a couple of unchanged lines of context.
- `CLAUDE.md` and `.claude/` are the author's controls and are never edited (decision 15): a change is a patch file in `proposals/` (a unified diff, checked with `git apply --check`) with the command to apply it, as in core2 and in this repo, whose own `CLAUDE.md` and `.claude/` are protected the same way. Nobody edits `third-party/`. The style is imported with `@third-party/core2/docs/style.md`, so it follows the pin.
- `CLAUDE.md` scopes its `third-party/` rules to sessions started at the client's root (decision 11). Claude Code also loads it in a session started in `third-party/core2`, because it is in a parent directory; without the scope line it would forbid the core2 work that session is for.
- `CLAUDE.md` also protects core2's sensitive parts as core2's own `CLAUDE.md` does (decision 9): `third-party/core2/src/`, `examples/`, `tools/`, `bench/support/` and its CMake build (`CMakeLists.txt`, `CMakePresets.json`, `cmake/`) never, not even comments, and no grant in the client covers them; `tests/` is written only in core2's repo; core2's `CLAUDE.md`, `docs/style.md` and `.claude/` are read, never changed.
- `.claude/settings.json`: sandbox enabled, `failIfUnavailable`, no unsandboxed commands, `filesystem.denyWrite` on `./CLAUDE.md`, `./.claude`, `./src`, `./CMakeLists.txt`, `./CMakePresets.json`, `./dev`, `./.clang-tidy` and `./third-party`, plus core2's own by name, as core2 `v2.0.0`'s `denyWrite` lists them (`./third-party/core2/src`, `tests`, `CMakeLists.txt`, `CMakePresets.json`, `cmake`, `bench/support`), for the Bash route; `deny` on `Edit(/CLAUDE.md)`, `Edit(/.claude/**)`, `Edit(/dev)` (core2's hook checks only C++, Makefile and CMake files, so `dev` takes no edits at all, comments included), `Edit(/.clang-tidy)` (the same) and `Edit(/third-party/**)`, plus core2's protected paths by name (`src/**`, `tests/**`, `examples/**`, `tools/**`, `bench/support/**`, `cmake/**`, `CMakeLists.txt`, `CMakePresets.json`, `CLAUDE.md`, `.claude/**`), for the file-tool route. The named entries repeat what `third-party` already covers, so they stay protected if that broad entry is ever narrowed; the `PreToolUse` comment-only hook on `Edit|Write|MultiEdit`, run from the submodule (`python3 "$CLAUDE_PROJECT_DIR"/third-party/core2/.claude/hooks/comment_only_guard.py`); `allow` for `Edit(/docs/**)`, `Edit(/proposals/**)`, `Edit(/README.md)`, `./dev build [<p>]`, `./dev run *`, `./dev docs`, `./dev help`, `cmake --preset <p>` and `cmake --build --preset <p>` for the four presets, and `cmake --build --preset debug --target docs` and `core2_docs`. core2 `v2.0.0`'s hook guards the client's root `CMakeLists.txt` (whole-line `#` comments only) and `CMakePresets.json` (no change), as it guarded the `Makefile`. `.claude/settings.local.json` is git-ignored.
- core2's `.claude/settings.local.json`, written by `./dev setup` into the submodule (core2 git-ignores it, so the submodule stays clean): `sandbox.filesystem.allowWrite` on the submodule's git directory (`git rev-parse --absolute-git-dir`, under the client's `.git/modules/`) with `denyWrite` on its `hooks/` and `config`, so Claude can commit in a core2 session (decision 11). The path is absolute, so `./dev setup` rewrites it on every run, and `./dev build` offers the setup when the path no longer matches (a moved project). `check.sh` checks its contents and that the submodule stays clean.
- The client's `CLAUDE.md` and `docs/core2.md` have the author run a pin bump's `fetch` and `checkout`: from Claude's sandbox the fetch needs `github.com:22`, and the checkout moves the submodule's `HEAD` and index but cannot write under `./third-party`. Claude checks the result (`status --short`, `describe --tags`).
- `.vscode/` (VS Code and VSCodium; checked with VSCodium and clangd 0.6.0, CMake Tools 1.25.10, CodeLLDB 1.12.3 from Open VSX): `extensions.json` recommends clangd, CMake Tools and CodeLLDB, and marks Microsoft's C/C++ extension unwanted; `settings.json` sets CMake Tools to the presets (`cmake.useCMakePresets: always`, `configureOnOpen`, status bar visible) and hides `docs/html` and `docs/core2` from the explorer. `cmake.debugConfig` (`"type": "lldb"`, `cwd` the project) puts CMake Tools' *Debug* command (Shift+F5, `cmake.debugTarget`) on CodeLLDB (2026-11-17): without a `type`, CMake Tools 1.25.10 builds a `cppdbg` configuration, which needs the unwanted Microsoft extension; with one, it skips that detection and merges the setting over `program`, `cwd`, `name`, `request` and `args: []`. CMake Tools keeps the selected preset only in the editor's workspace state (`initializeKitOrPresets` reads `configurePresetName` from it; 1.25.10 has no setting for a default), so the first open asks once; `debug` is first in the list. clangd (`"C_Cpp.intelliSenseEngine": "disabled"`, `--compile-commands-dir=${workspaceFolder}/build/cmake/debug`, `--header-insertion=never` so completion adds no standard-library `#include`s, `--background-index`, `--completion-style=detailed`, `--clang-tidy`, `*.cppm` as C++); `launch.json` runs `build/cmake/debug/<project-name>` under CodeLLDB (`"type": "lldb"`) after `build-debug`, with `args: []` (the client's README shows fixed `args` and `promptString` inputs); `tasks.json` has `build-debug` (default) and `build-release`, each `cmake --build --preset <p>`.
- `.gitignore`: `/build`, `/.cache`, `compile_commands.json`, `vgcore*`, `/.claude/settings.local.json`, `/proposals`, `/docs/html`, `/docs/latex`, `/docs/core2`, `.idea` (the sandbox mounts `/dev/null` there).
- `.clang-tidy` (2026-11-17) puts core2's `docs/style.md` into checks; core2 has no `.clang-tidy` of its own. Chosen by running every check family over core2 `v2.1.8` (`src/`, `tests/`, `examples/`, 94 files) and keeping what core2 already passes or what finds bugs, and by the author's answers: trailing return types on functions, not lambdas (`TransformLambdas: none`; 73 lambdas in core2 have none); `UPPER_CASE` for namespace-scope, static and class constants, `camelBack` for local ones, `is`/`has` variable templates exempt (`isOption<T>`); `cppcoreguidelines-init-variables` on (25 `u64 n;` in core2's `src/`). Enabled: `bugprone-*`, `performance-*`, `portability-*`, `misc-*` minus the exclusions below, a short `modernize-*` and `readability-*` list (trailing return type, `nullptr`, `override`, `using`, `= default`/`= delete`, `[[nodiscard]]`, else-after-return, the `redundant-*` checks, misleading indentation), `readability-identifier-naming` (`PascalCase` types, concepts, enums and their values and template parameters; `camelBack` functions, members, parameters and variables; `lower_case` namespaces; `UPPER_CASE` macros), and `cppcoreguidelines-init-variables`, `-avoid-goto`, `-pro-type-member-init`, `-slicing`. Left out, as against the style or noise on core2 (hits in core2 in parentheses): the checks that want the standard library, C casts (863), C arrays (643), pointer arithmetic, unions, varargs, braces on one-line `if`s (1381), `misc-const-correctness` (1623), magic numbers (3131), identifier length (3586), `misc-include-cleaner` (2453, wrong for modules), `misc-use-anonymous-namespace` and `-use-internal-linkage` (modules use `detail`), `misc-explicit-constructor` (core2's conversions are implicit on purpose), `bugprone-signed-bitwise` (380), `bugprone-easily-swappable-parameters`, `performance-no-int-to-ptr` (allocators), `portability-avoid-pragma-once`, and `readability-redundant-inline-specifier`, which would remove the `inline` style.md requires for inlining across modules. `clang-analyzer-*` is off: clangd 23 does not run it, and `clang-tidy` from a terminal follows calls into core2 and reports false positives there (a garbage value at `fmt.cppm:957`, for a buffer `num::writeU64` fills) on a clean `main.cpp`. `HeaderFilterRegex` takes the project's `src/` headers, `ExcludeHeaderFilterRegex` drops `third-party/`. With it, core2's feature modules have only `formatError_*`/`matchError_*` (consteval error names) and two local constants left in naming, plus the uninitialized locals. `third-party/.clang-tidy` (`Checks: '-*'`) turns the checks off for files under `third-party/`, which clangd would otherwise check with the client's file when one is opened (33 diagnostics on core2's `types.cppm` without it, none with it). The client protects `.clang-tidy` like `CMakePresets.json` (`deny` and `denyWrite`); `third-party/` is protected already.
- The client's README also notes clang 23's missing debug info for core2 templates instantiated across modules (`<incomplete type>` in the debugger), with the workaround.
- No tests in generated clients for now (decision 4).

## check.sh
For each variant: `copier copy --trust --defaults --vcs-ref=HEAD` from this repo into a temp dir, with every question answered by `--data` (`core2_url` and `core2_version` are the defaults read from `copier.yml`, so what users get is what gets checked; `CORE2_DIR` swaps in a local clone, and `CORE2_VERSION` another tag). `--vcs-ref=HEAD` with a local path includes uncommitted changes. Copier's task runs `./dev setup` (with a local clone, `protocol.file.allow=always` is in the environment, which git needs to clone a local path as a submodule). Then: the debug build and its `compile_commands.json`, where `.vscode/settings.json` points clangd; sanity checks on the tree (no `copier.yml`, `ui/` or `*.jinja` left, exactly one `src`, no Jinja tags outside `src/`, `third-party/`, `build/` and `docs/core2/`, the JSON files parse, `CMakePresets.json` and `.vscode/extensions.json` included, the hook's self-test passes from the submodule, core2's `settings.local.json` and a clean submodule); core2's reference and tag file from `setup.sh`, git-ignored; `./dev` (executable; away from a terminal, help for no command and an error for an unknown preset; in a copy without the setup, `./dev build` stops and names `./dev setup`; `./dev clean release` removes only that preset); and a second `./dev setup`, which must pass and leave the pin. The presets are built and the binaries run through `./dev build` and `./dev run`. Then:
- Without the submodule: `CMakeLists.txt`, `CMakePresets.json` and `src/` copied into an empty directory; `cmake --preset debug` there must fail with the `git submodule update --init` message.
- Every preset: `cmake --preset <p>`, then `cmake --build --preset <p>`; a `warning:` or `CMake Warning` in either fails the check. Then the runs below.
- `build/cmake/debug/compile_commands.json` must have entries for `src/main.cpp` and for core2, and `third-party/core2` must still be clean after all the builds (CMake writes only under the client's `build/`).
- `clang-tidy -p build/cmake/debug --warnings-as-errors='*' src/main.cpp` must pass: each variant's `main.cpp` keeps to the client's `.clang-tidy`.
- The `docs` target must pass with no warning, write `docs/html/index.html` (git-ignored) with the link to `docs/core2/html/index.html`, which must resolve from `docs/html/`; the README must have the link too.

The runs, in every preset:
- `plain`, and `ncurses` without a terminal: run with two arguments; the output is checked.
- `ncurses` on a pseudo-terminal (`script`, when installed): the screen must show the arguments and the prompt; a key press ends it.
- `sdl3` and `imgui` + `sdl3_renderer`: run on SDL's `offscreen` video driver (no window on the desktop). `check.sh` waits up to 20 seconds for the line each prints once its window is set up, lets it draw for one more second, then stops it; exiting on its own, or no line in time, fails. It reports how long setup took. It replaced a fixed 2-second limit, which `glfw_vulkan`'s instrument build missed on the author's desktop: under the sanitizers its window is up after 2.6 seconds, against 0.3 in the other modes (2026-10-31), most likely the Vulkan loader loading this machine's three drivers (Intel, Intel hasvk, NVIDIA).
- `imgui` + `sdl3_gpu`, `glfw_opengl3`, `glfw_vulkan`: built only. They need a surface that can present, which the offscreen driver lacks (SDL_GPU fails with "This surface does not support presenting!"). `WINDOWED=1 ./check.sh` runs them the same way on the real display.

The binaries run in the project's directory, where ImGui writes `imgui.ini`. ImGui comes from GitHub over HTTPS (`./dev setup`), so the ImGui variants need the network.

`./check.sh plain` is the usual check (about 15 seconds); all seven variants take about five minutes and run when the author asks.
